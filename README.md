# 🦔 Ezhik Guard

Централизованная защита VPN-нод Xray / Remnawave от торрентов, P2P-рассылок и
сканирования портов, единое управление SSL-сертификатами, firewall, Nginx и
сайтами-заглушками нод. Одна панель с веб-интерфейсом, лёгкий агент на каждой ноде.

```text
Developer : ezhikdev
Telegram  : @ezhikdev
GitHub    : https://github.com/ezhikdev
Version   : 2.2
```

Ezhik Guard объединяет **Ezhik Torrent Guard 1.x** и **Ezhik SSL Manager**. Нарушение
привязывается к точному числовому ID клиента Xray, и блокируется только его
подписка через Remnawave API — общий IP пользователей не страдает.

## Возможности

**Панель**
- установка одной неизменной командой, обновление — кнопкой в интерфейсе;
- добавление ноды: панель выдаёт одноразовую команду, нода подключается сама;
- обновление агентов одной кнопкой (по одной ноде или всех сразу), проверка
  SHA-256 и автоматический откат, если новая версия не запустилась;
- обзор: ноды на связи, обнаружения по времени, блокировки, частые нарушители,
  истекающие сертификаты;
- ноды: состояние, uptime и доступность по часам, CPU/RAM/диск/сеть, версия
  агента, компоненты защиты, диагностика с подсказками, события ноды;
- массовые действия и фильтры для большого числа нод;
- журнал событий, реестр блокировок (снять сейчас, продлить, удерживать,
  защищённые клиенты), карточка клиента с данными из Remnawave;
- уведомления в Telegram с текстовыми отчётами для ответа хостеру;
- журнал аудита, сессии администратора, светлая и тёмная темы, мобильная версия.

**Защита (общие настройки для всех нод, включение на каждой ноде отдельно)**
- BitTorrent: Suricata 8.0.6 + strict nDPI 4.14 и точная атрибуция
  `Xray request → client ID → outbound socket → nDPI alert`;
- P2P / DHT fan-out: клиент обращается к сотням несвязанных хостов на случайных
  портах (шифрованный торрент, DHT, uTP) — именно это хостеры присылают как
  «portscan»;
- сканирование портов: перебор портов одного IP и плотный скан подсети /24;
- режимы «наблюдение» и «блокировка», длительность заморозки, пороги;
- один реестр блокировок для всех нод: один нарушитель — одна санкция,
  автоматическая разблокировка по истечении срока.

**Сертификаты**
- собственный ACME-клиент (Let's Encrypt, DNS-01), без certbot;
- wildcard любой глубины: `*.domain.com`, `*.test.domain.com`,
  `*.sub.test.domain.com`, вместе с `domain.com` в одном сертификате (SAN);
- подсказки о покрытии: `*.domain.com` не покрывает `domain.com` и `a.b.domain.com`;
- DNS-провайдеры: Cloudflare (API-токен), acme-dns (любой DNS-хостинг через один
  CNAME), ручная публикация TXT-записей;
- автопродление и автоматическая доставка новой версии на назначенные ноды;
- назначение сертификата ноде, смена, отключение с удалением файлов;
- загрузка собственного сертификата; сертификат можно назначить и самой панели;
- HTTP-01 через порт 80 панели — для одиночных доменов без доступа к DNS API.

**Новое в 2.2.3**
- **свой порядок нод**: перетащите ноду за ручку ⠿ в списке «Ноды» (мышью или
  пальцем) либо сфокусируйте ручку и двигайте стрелками ↑/↓; порядок
  сохраняется на панели и одинаков везде — в списке, на обзоре, в выборе нод.
  Пока включены фильтр или поиск, порядок не меняется;
- **новый дизайн в стиле Ezhik VPN WebApp** («Ezhik Expressive»): тональные
  поверхности, тёплый персиковый акцент, навигационная рельса с перетекающим
  индикатором, кнопки-«пилюли», которые при нажатии становятся скруглённым
  квадратом, волна от точки нажатия, пружинная анимация, переключатели с
  галочкой, снекбары, смена темы раскрывающимся кругом; на телефоне — плавающая
  верхняя панель, меню-шторка и диалоги снизу. При «уменьшить движение» в ОС
  анимации отключаются.

**Новое в 2.1**
- **HTTPS панели по домену**: проверка A/AAAA и доступности, Let's Encrypt
  (HTTP-01 или DNS-01) с автопродлением, стандартный порт 443 и редирект с 80,
  безопасный переход — доступ по IP:8443 сохраняется всегда;
- **Firewall Manager**: глобальные правила + переопределения на ноде, TCP/UDP,
  диапазоны, IPv4/IPv6, CIDR; автообнаружение портов Xray/RemnaNode/Nginx/Docker
  с политиками «открыт / белый список / закрыт»; своя таблица nftables, проверка
  `nft -c`, защита SSH, автоматический откат при потере связи с панелью;
- **Nginx Manager**: режим ноды Direct (как раньше), Vision + TLS Fallback (2.2) или Frontend — Nginx на 80/443,
  TLS 1.2/1.3, 301 на HTTPS, сайт-заглушка и маршруты gRPC (`grpc_pass`),
  WebSocket, HTTPUpgrade, XHTTP во внутренние inbound'ы Xray; проверка
  совместимости с inbound'ами Remnawave и синхронизация одного inbound'а
  (`listen`, `port`, `security: none`, `serviceName`/`path`) через API Remnawave;
- **сайты-заглушки**: загрузка ZIP, общий сайт и индивидуальные для нод, версии
  с черновиком, «Предпросмотр сайта» на `https://домен-панели/site-mask/`,
  распространение на ноды со статусами;
- **TCP BBR** (+ fq) — глобально, на ноде или массово;
- массовое включение firewall и BBR на выбранных нодах.

## Совместимость

| Компонент | Поддержка |
|---|---|
| Ubuntu | 22.04 LTS, 24.04 LTS (amd64) |
| Remnawave Panel | 3.x (проверено с 3.4.4) и 2.x — версия API определяется автоматически |
| RemnaNode | старые и новые версии: ID клиента в логах Xray (`email`) не менялся |
| Xray-core | форматы логов проверены по исходникам v26.7.28 (RemnaNode 3.x) |

Панели Remnawave 3.x принимают запросы только через HTTPS reverse proxy. Если
Ezhik Guard стоит на том же сервере, можно указать `http://127.0.0.1:3000`:
панель сама добавит заголовки `X-Forwarded-For` / `X-Forwarded-Proto`.

**Remnawave 3.x.** В ветке 3 у пользователей больше нет `uuid`, удалён
`GET /api/users/by-id/{id}`, все маршруты (`/api/users/{id}`,
`/actions/disable`, `/actions/enable`) принимают числовой ID. Torrent Guard 1.x
на панели 3.x не мог разблокировать и блокировать пользователей. Ezhik Guard
определяет версию через `/api/system/metadata` (или пробой маршрутов, если у
токена нет этого права), работает с обеими ветками и сам переключается после
обновления Remnawave. Блокировки, выданные на 2.x, корректно снимаются после
перехода на 3.x.

## Установка панели

На сервере для панели (это может быть и одна из нод) от root:

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/ezhikdev/ezhik-torrent-guard/main/install.sh)
```

Команда **не меняется между версиями**: она всегда ставит последний релиз.
Установщик спросит адрес панели для нод и порты (по умолчанию веб-интерфейс
`8443`, API агентов `8444`) и в конце покажет адрес, логин `admin` и пароль.

Полезные варианты:

```bash
# сразу защитить и этот сервер (поставить агент локально)
bash <(curl -fsSL .../install.sh) --with-node
# конкретная версия / неинтерактивно
bash <(curl -fsSL .../install.sh) --version 2.1.0 --yes
# сбросить пароль администратора
bash <(curl -fsSL .../install.sh) --reset-password
```

Порты `8443` (для вас) и `8444` (для нод) должны быть доступны. Веб-интерфейс
сначала использует сертификат собственного CA панели — браузер покажет
предупреждение. Подключите домен в «Настройки → Панель → Домен и HTTPS панели»
(см. ниже) или выпустите сертификат во вкладке «Сертификаты» и назначьте его
панели (применяется без перезапуска).

После входа:
1. **Настройки → Remnawave**: адрес панели и API-токен, кнопка «Проверить».
2. **Настройки → Защита**: режимы и длительности (по умолчанию торренты —
   блокировка, P2P и сканирование — наблюдение).
3. **Ноды → Добавить ноду**.

## Домен и HTTPS панели

«Настройки → Панель → Домен и HTTPS панели»:

1. Создайте A (и при необходимости AAAA) запись домена на IP панели и нажмите
   «Проверить»: панель сравнит записи с адресами сервера и проверит доступность.
2. Выберите проверку Let's Encrypt: **HTTP-01** (панель займёт порт 80) или
   **DNS-01** через провайдера из «ACME и DNS».
3. По желанию: стандартный порт 443 (`https://домен/`), редирект 80 → HTTPS,
   использование домена в новых командах установки агентов.

Порт `8443` и доступ по IP продолжают работать всегда; интерфейс переключается на
новый сертификат только после успешного выпуска; «Отключить домен» возвращает
прежнее состояние. Работающие агенты не затрагиваются: канал к ним защищён CA
панели, а не публичным сертификатом.

Если на сервере панели нода работает в режиме Nginx Frontend, порты 80/443 занимает
Nginx — для домена панели используйте DNS-01 и порт 8443. Для продления через
HTTP-01 порт 80 панели должен оставаться включённым (интерфейс предупредит).

## Firewall

«Firewall» в меню — глобальные правила для всех нод (по умолчанию разрешены
TCP 22, 80, 443) и политики для обнаруженных портов; на странице ноды —
переопределения для отдельных портов и собственные правила.

- Агент сообщает, что слушает на ноде (`ss`, IPVS), панель добавляет inbound'ы из
  Remnawave и порты Nginx. Политики по умолчанию: inbound'ы Xray, Nginx, IPVS,
  Docker и прочие службы открыты (работающие службы не ломаются), API RemnaNode —
  только для IP панели Remnawave и белого списка, upstream-порты маршрутов Nginx
  закрыты снаружи.
- Ezhik Guard создаёт **собственную таблицу** `inet ezhik_guard` и не трогает
  цепочки Docker, ufw, fail2ban и чужие правила; трафик опубликованных портов
  Docker фильтруется в forward.
- Применение: проверка `nft -c`, атомарная загрузка, проверка связи с панелью;
  если связь потеряна — откат сразу, а если агент завис — systemd-таймер вернёт
  прежнюю таблицу через заданное время (по умолчанию 90 с). SSH всегда открыт,
  установленные соединения не рвутся.
- Firewall выключен по умолчанию: включите его на ноде (или массово) после
  проверки списка обнаруженных портов. Выключение удаляет таблицу целиком.

## Nginx Frontend

На странице ноды → «Nginx»:

- **Direct** — как раньше: Nginx не используется, Xray сам слушает порты и
  обрабатывает TLS. При переключении в Direct Ezhik Guard удаляет только свой
  конфиг, возвращает стоковый сайт Nginx и останавливает Nginx, если ставил его сам.
- **Frontend** — Nginx принимает 80/443 (301 на HTTPS), TLS 1.2/1.3 с сертификатом
  ноды, показывает сайт-заглушку и проксирует маршруты во внутренние inbound'ы Xray
  без TLS. Пример: порт 443, gRPC, `serviceName: cdn-service`, Xray
  `127.0.0.1:10443` → Nginx отдаёт `/cdn-service/Tun` в Xray (`grpc_pass`), всё
  остальное — сайту.

Перед применением агент проверяет транспорт (REALITY/RAW/mKCP/QUIC через HTTP
нельзя), занятость портов другими процессами и чужими конфигами Nginx, доступность
`127.0.0.1` из сети контейнера RemnaNode и `nginx -t`, затем — отвечают ли 443 и
маршрут gRPC; при любой ошибке возвращается прежняя конфигурация.

Колонка «Совместимость» сравнивает маршрут с inbound'ом Remnawave. Кнопка
«Исправить в Remnawave» показывает изменения «было/станет» и меняет в профиле
**только этот inbound** (`listen`, `port`, `security: none`,
`serviceName`/`path`) через API Remnawave — подписки пересоберёт сама Remnawave.
REALITY и смена транспорта автоматически не выполняются.

## Vision + TLS Fallback

Третий режим Nginx (с 2.2): **Xray принимает TLS на 443** (VLESS RAW + TLS +
XTLS Vision), а всё, что не является VLESS, через fallbacks Xray попадает в
Nginx на локальных портах. Корректные клиенты с `flow: xtls-rprx-vision` получают
туннель, обычный браузер — сайт-заглушку с сертификатом ноды.

```text
клиент VLESS Vision ─┐                    ┌─► туннель (inbound Vision)
браузер (h2 / 1.1) ──┼─► Xray :443 (TLS) ─┤
gRPC / WS клиенты ───┘                    └─► fallback ─► Nginx 127.0.0.1:8001 (HTTP/1.1)
                                                          Nginx 127.0.0.1:8002 (h2c)
                                                            ├─ сайт-заглушка
                                                            └─ маршруты gRPC/WS/XHTTP → Xray
```

- Для Vision нужен **отдельный VLESS inbound** (RAW, не REALITY) в профиле
  Remnawave. REALITY и inbound'ы gRPC/WS/XHTTP не меняются; маршруты Nginx на
  443 продолжают работать через fallback (gRPC — через HTTP/2).
- Сертификат — из SSL Manager. Xray читает его **внутри контейнера RemnaNode**
  (`/etc/xray/ssl/…` по умолчанию), поэтому установка сертификата должна быть
  «в Docker-контейнер» (или каталог смонтирован). Агент проверяет это до
  любых изменений.
- Посетители получают HTTP/1.1 и HTTP/2 (ALPN `h2, http/1.1`), Nginx видит их
  реальный IP через PROXY protocol (`xver 1`); порт 80 отдаёт 301.

Как включить: страница ноды → «Nginx» → **Vision + TLS**, выбрать inbound →
«Синхронизировать с Remnawave», посмотреть «было/станет» и подтвердить.
Порядок безопасный: агент проверяет порты, сеть контейнера (нужна `host`) и
сертификат, переводит Nginx на локальные порты (`nginx -t`, проверка ответов,
откат при ошибке); изменение inbound в Remnawave выполняется только после
этого (можно подтвердить заранее — оно запустится, как только агент будет
готов). Порт 443 недоступен около 10 секунд, пока RemnaNode перезапускает Xray.

Изменяется только выбранный inbound: `listen 0.0.0.0`, `port 443`,
`security: tls` с сертификатом, `alpn`, `flow: xtls-rprx-vision`, `fallbacks`,
`decryption: none`. Клиенты, sniffing и другие ключи остаются. Если inbound
активен ещё на других нодах общего профиля — автоматическое изменение
запрещено (оно затронуло бы их). Если inbound раньше был без TLS, клиентам
нужно обновить подписку.

Обратно: Vision → Direct — Nginx отключается, VPN продолжает работать, сайт
перестаёт отвечать. Vision → Frontend — сначала уберите inbound Vision с 443 в
Remnawave, иначе агент откажется (порт занят Xray) и оставит Vision работать.

## Сайты-заглушки

«Сайты» в меню: загрузите ZIP со статическим сайтом (`index.html` в корне или в
единственной папке; HTML, CSS, JS, изображения, шрифты, медиа). Архив проверяется:
запрещены `..`, абсолютные пути, ссылки, zip-бомбы; серверные скрипты (PHP и т. п.)
отбрасываются. Первая версия публикуется сразу, следующие сохраняются черновиком —
проверьте предпросмотр и нажмите «Опубликовать». Ноды получают сайт автоматически,
статус виден в таблице «Распространение на ноды»; ноде можно назначить
индивидуальный сайт.

«Предпросмотр сайта» открывает `https://домен-панели/site-mask/`: стили, картинки,
JS-модули, `fetch` и переходы работают, корневые пути `/css/...` переписываются.
Сайт выполняется в изолированной песочнице (CSP sandbox, отдельный origin): его
скрипты не видят cookies, хранилище и API панели.

## Подключение ноды

1. **Ноды → Добавить ноду**, введите название.
2. Скопируйте показанную команду и выполните её на ноде от root.
3. Окно само покажет, что нода подключилась.

Требования к ноде: Ubuntu 22.04/24.04 amd64, Docker с контейнером RemnaNode,
логи Xray в RAM:

```json
"log": {
  "access": "/dev/shm/xray-access.log",
  "error": "/dev/shm/xray-info.log",
  "loglevel": "info"
}
```

Задайте этот блок в Config Profile Remnawave. Без него точная атрибуция
невозможна — диагностика ноды подскажет. Подробнее:
[docs/XRAY_LOGGING.md](docs/XRAY_LOGGING.md).

**Старый Torrent Guard 1.x и агент SSL Manager удаляются автоматически**:
останавливаются и удаляются их сервисы, файлы, runtime и помеченные `ezhik`
правила firewall; конфигурация архивируется в `/var/backups/ezhik-guard/agent`;
активные блокировки 1.x и список защищённых клиентов передаются в панель.
Посторонние сервисы, пакеты и правила не затрагиваются. Сертификаты в
`/etc/xray/ssl` остаются на месте.

Агент работает и при недоступной панели: защита продолжает обнаруживать
нарушения, события копятся на диске и доставляются после восстановления связи.

## Обновление

- **Панель**: «Настройки → Обновления → Обновить панель» или повтор команды
  установки. База и настройки сохраняются; если новая версия не стартует,
  установщик вернёт предыдущую.
- **Агенты**: после обновления панели на странице «Ноды» появится «Обновить все»
  (или кнопка на странице ноды). Нода скачивает агент с панели, проверяет SHA-256
  и перезапускается; при сбое запуска она сама откатывается и сообщает об этом.
- **Ubuntu 24.04, агент 2.0.x–2.1.1**: в systemd ≥ 254 старый юнит агента
  принимает плановый перезапуск после обновления за сбой, и обновление сразу
  откатывается (событие «Обновление агента … откатено» с подсказкой). Один раз
  выполните на такой ноде и повторите обновление — с 2.1.2 юнит исправлен:

  ```bash
  mkdir -p /etc/systemd/system/ezhik-guard-agent.service.d && \
  printf '[Service]\nSuccessExitStatus=75\n' > /etc/systemd/system/ezhik-guard-agent.service.d/10-restart.conf && \
  systemctl daemon-reload
  ```

## Как работает защита

```text
             RemnaNode (Docker)                         Нода
  клиент ──► Xray ── access/info логи в RAM ──► агент Ezhik Guard ─┐
                │                                   ▲               │ события
                └── исходящий сокет ── Suricata + strict nDPI ┘     ▼
                                                              Панель Ezhik Guard
                                                         политика · реестр блокировок
                                                                    │
                                                         Remnawave API (2.x/3.x)
```

- **BitTorrent**: санкция только после однозначного сопоставления nDPI-алерта
  с реальным сокетом Xray и ID клиента; неоднозначные случаи пропускаются.
- **P2P fan-out**: учитываются UDP/TCP-назначения на портах ≥ 1024, кроме
  типовых сервисных (QUIC/HTTPS, STUN, Zoom и т. п.); порог по умолчанию —
  120 хостов из 40 разных сетей /16 за 60 с (TCP: 150 / 50).
- **Сканирование**: 50 TCP-портов (100 UDP) одного IP или 16 хостов / 50 портов
  / 100 назначений в одной /24 за 60 с.

Все пороги настраиваются в «Настройки → Защита → Пороги». Новые правила стоит
сначала проверить в режиме наблюдения на реальной нагрузке.

Правила безопасности блокировок (из 1.x, сохранены): блокируется только
пользователь в статусе ACTIVE; уже отключённый кем-то пользователь никогда не
включается автоматически; неоднозначные ответы API (таймаут, 5xx) запоминаются
и распознаются при повторе; автоматическое включение — только для «своей»
блокировки, если пользователь не был пересоздан.

## Сертификаты

1. «Настройки → ACME и DNS»: e-mail Let's Encrypt, DNS-провайдер.
2. «Сертификаты → Новый сертификат»: домены (например, `example.com`,
   `*.example.com`, `*.test.example.com`), провайдер, тип ключа.
3. На странице ноды → «SSL-сертификат»: выбрать сертификат, домен ноды (для
   проверки покрытия), куда ставить (Docker-контейнер, systemd или файлы) и как
   применять (перезапуск, без перезапуска — если в профиле Xray включён
   `ocspStapling`, или своя команда).

Для `*.sub.test.example.com` TXT-запись проверки — `_acme-challenge.sub.test.example.com`;
для `example.com` и `*.example.com` используется одна запись с двумя значениями.
С провайдером acme-dns для каждого такого имени один раз создаётся CNAME.

## Безопасность

- агенты доверяют только собственному CA панели (ключ пиннится в команде
  установки); токен ноды индивидуален и хранится с правами `0600`;
- секреты (токены Remnawave, Cloudflare, Telegram) зашифрованы в базе панели;
- вход в панель: scrypt, HttpOnly-сессии, CSRF-защита, ограничение попыток;
- панель работает от отдельного пользователя с ограничениями systemd;
- сетевые метаданные — только в RAM (`/dev/shm`), без PCAP и payload;
- детектор пассивен (AF_PACKET) и не перехватывает трафик; правила nftables
  появляются только при включённом Firewall и только в собственной таблице;
- изменения Nginx, firewall, BBR и сайта выполняются агентом с резервной копией,
  проверкой и автоматическим откатом; действия администратора пишутся в аудит.

## Удаление

Ноду лучше удалять в панели («Удалить ноду»): агент сам удалит свои компоненты.
Вручную:

```bash
bash /opt/ezhik-guard/panel/current/uninstall.sh --agent   # агент
bash /opt/ezhik-guard/panel/current/uninstall.sh --panel   # панель (с резервной копией)
```

## Ограничения

- анализируются публичные IPv4-назначения; IPv6 и ICMP пока не анализируются;
- Suricata-runtime собран для amd64 (Ubuntu 22.04 и 24.04);
- процессы на самом VPS и трафик в обход Xray нельзя связать с клиентом;
- поведенческие детекторы срабатывают по порогу: первые запросы проходят;
- ручной DNS-режим сертификатов требует ваших действий при каждом продлении —
  для автоматики используйте Cloudflare или acme-dns;
- режим Vision требует RemnaNode в сети `host` (fallback идёт на 127.0.0.1) и
  отдельный VLESS inbound; в общем профиле Remnawave его нужно настроить вручную;
- Nginx Frontend и HTTPS панели на порту 443 на одном сервере конфликтуют за
  80/443 — используйте для панели порт 8443 и DNS-01;
- через Nginx проходят только gRPC, WebSocket, HTTPUpgrade и XHTTP; REALITY и RAW
  остаются в режиме Direct на отдельном порту;
- предпросмотр заглушки максимально близок к ноде, но URL, собранные скриптами
  нестандартно (например, в Web Worker), могут вести себя иначе, чем на ноде.

## Разработка

```text
agent/   агент ноды (Python stdlib)      panel/  панель (FastAPI + SQLite)
web/     интерфейс (Preact + Vite)       packaging/ установка агента, самообновление
tests/   unit, mock Remnawave/Cloudflare, интеграционный стенд
```

```bash
python -m unittest discover -s tests/agent -t tests/agent
python -m unittest discover -s tests/panel -t tests/panel
python scripts/build_release.py          # dist/ezhik-guard.tar.gz
```

Релиз публикуется GitHub Actions по тегу `v<VERSION>`. Suricata-runtime
собирается отдельным workflow «Build Suricata runtime» только при изменении
`RUNTIME.env`. Подробности для хостеров: [docs/HOSTER_PORT_SCAN_PROTECTION_RU.md](docs/HOSTER_PORT_SCAN_PROTECTION_RU.md).
