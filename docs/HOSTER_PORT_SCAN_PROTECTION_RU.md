# Техническое описание защиты от исходящего сканирования портов

На сервере внедрён поведенческий детектор исходящего сканирования портов,
интегрированный с Xray/Remnawave. Его задача — не просто обнаружить большое
число соединений с публичного IP сервера, а определить конкретную VPN-подписку,
которая создала эти соединения, и отключить именно её.

## Источник событий и атрибуция клиента

Xray формирует access-событие для каждого принятого от авторизованного клиента
TCP- или UDP-запроса. Событие содержит:

- числовой идентификатор клиента Remnawave;
- протокол TCP или UDP;
- запрошенный IPv4-адрес и порт назначения;
- время запроса.

Детектор непрерывно читает access-log Xray из RAM (`/dev/shm`). Попытка
учитывается сразу после того, как Xray принял запрос клиента, поэтому для
обнаружения не требуется успешное TCP-соединение: обращения к закрытым портам
тоже попадают в анализ. Для успешно открытых соединений дополнительно
используется сопоставление outbound-сокета Xray; одинаковые события
дедуплицируются по сочетанию `protocol + destination IP + destination port`.

Ingress-IP пользователя не используется для назначения санкции. Это исключает
ошибочную блокировку из-за NAT, общего адреса, переподключения или нескольких
пользователей за одним входным IP. Санкция применяется только к числовому ID,
который Xray записал в событии авторизованного запроса.

## Алгоритм обнаружения

Для каждого клиента независимо поддерживаются скользящие окна событий в
оперативной памяти. По умолчанию нарушение фиксируется при выполнении хотя бы
одного условия:

1. Последовательный перебор портов одного адреса: не менее 20 уникальных портов
   одного IPv4-адреса за 60 секунд.
2. Сканирование подсети: не менее 16 адресов одной подсети `/24` и не менее
   50 уникальных портов за 60 секунд.
3. Распределённый всплеск: не менее 100 уникальных сочетаний `IP:port` и не
   менее 50 уникальных портов за 15 секунд.

Повтор одного назначения внутри окна не увеличивает счётчик. Для снижения риска
ложных срабатываний недостаточно просто создать много соединений: требуется
разнообразие портов. Например, большое количество обычных HTTPS/QUIC-соединений
к порту 443 не соответствует критериям сканирования. Частные, служебные и
непубличные IPv4-адреса из анализа исключаются. После инцидента действует
пятиминутное подавление повторных уведомлений для того же клиента.

## Реакция на нарушение

Предусмотрено два независимых режима:

- `OBSERVE` — обнаружение, журналирование и уведомление без блокировки;
- `LIVE` — обнаружение с автоматическим отключением точной подписки через
  Remnawave API.

В режиме `LIVE` событие помещается в ограниченную очередь действий. Перед
отключением проверяются корректность числового ID, список защищённых клиентов,
отсутствие уже выполняемой санкции и текущее состояние пользователя в
Remnawave. После этого API-запросом отключается только выявленный клиент.

Срок санкции настраивается в минутах. Значение `0` означает бессрочное
отключение: после подтверждённого статуса `DISABLED` клиент может быть включён
вручную администратором в Remnawave Panel. При конечном сроке состояние санкции
сохраняется минимально необходимым образом и клиент автоматически включается
после истечения установленного времени.

Для каждого подтверждённого события создаётся локальный текстовый отчёт и
отправляется Telegram-уведомление администратору. Отчёт содержит время UTC, IP
ноды, ID клиента, тип детектора, агрегированные счётчики, срок реакции и
ограниченный список назначений. Файлы имеют права `0600`, каталог — `0700`,
хранятся только последние 100 отчётов. Токен Telegram хранится отдельно с
правами `0600` и не выводится в журналы.

## Влияние на сеть и ресурсы

Port-scan detector работает пассивно и не находится в тракте передачи пакетов:
он не добавляет правила `iptables`, не использует `NFQUEUE`, не изменяет
маршрутизацию и не выполняет дополнительный DPI payload. Обработка сводится к
разбору уже существующих событий Xray и обновлению счётчиков в RAM. Очередь
уведомлений ограничена, устаревшие элементы окон регулярно удаляются.

Так как защита поведенческая, несколько первых запросов проходят до достижения
порога. После достижения порога в `LIVE` блокируется сама VPN-подписка, что
прекращает последующий исходящий трафик этого клиента через ноду.

## Текущий этап внедрения и ограничения

На тестовой ноде включён режим `OBSERVE`. Контрольный последовательный TCP-скан
был обнаружен на пороге 20 портов, корректно сопоставлен с ID тестового клиента,
записан в журнал и отправлен администратору вместе с отчётом. После проверки
обычного веб-трафика, видео и игр на отсутствие ложных срабатываний предусмотрено
включение режима `LIVE`.

Текущая версия анализирует TCP/UDP назначения с публичными IPv4-адресами. IPv6,
ICMP, процессы, запущенные непосредственно на самом сервере, и любой отдельный
маршрут в обход Xray не относятся к атрибутируемому трафику VPN-клиентов и
требуют отдельного контроля средствами firewall/IDS.
